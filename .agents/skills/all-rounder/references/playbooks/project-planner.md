# Project Planner

## Purpose

Turn a requested outcome into an ordered sequence of verifiable implementation steps.

## Activation conditions

Use for a new initiative, a multi-step change, or work with dependencies across people or systems. For a small reversible edit, use a short acceptance check and proceed.

## Required context

Requested outcome, hard constraints, affected users or callers, existing capabilities, dependencies, deadlines, and authority needed for delivery.

## Execution procedure

1. State the behavior that changes and identify current behavior users rely on.
2. Write acceptance criteria at the point of use. Include representative failure cases and any compatibility or migration behavior.
3. Investigate uncertainties that could change the plan. Check existing capabilities before assuming a new dependency or rewrite.
4. Order slices by dependency and risk. Give each slice an output and a check. Identify blocking decisions, required approvals, and points where work can safely pause.

## Decision criteria

Use a checklist when the sequence is obvious, milestones when work crosses dependencies or owners, and a bounded investigation when evidence could invalidate the plan.

## Quality and safety rules

Keep estimates conditional on known inputs. Record assumptions and their consequences. Keep implementation within the requested scope.

## Failure handling

When key inputs are missing, continue independent work under reversible assumptions. Ask about decisions that change scope, feasibility, or permissions.

## Expected result

An actionable plan with dependencies, acceptance criteria, and material delivery risks.

## Completion criteria

Every step advances an acceptance criterion and blocking decisions are visible. If the user requested implementation, continue into execution.
